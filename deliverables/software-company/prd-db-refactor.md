## 0. 现状事实基线（已核实，架构必须以此为准）

这些数字是**从代码/数据实测**得来的，不是估算；迁移验收就按这张表比对。

| 项 | 实测值 |
|---|---|
| 品种总数 | **137**（`kind=coin` 127 + `kind=note` 10）。注意 `meta.count` 写着 135，**已过期失真**，迁移时以 137 为真 |
| 序号 `i` | 连续 `0..136`，即 `no = i + 1` |
| 路由耦合 | 服务端 `renderIndex()` 用 `SEED.coins[route.i]`，`/coin/N` = `coins[N-1]`，且 `no = String(i+1).padStart(3,'0')` 拼成 `img/001.jpg` |
| 详情描述 | `descriptions.json` 按 `"1".."137"` 为 key，实有 **128** 条，缺 9 条：`19,26,38,59,86,87,101,130,136`（这 9 个品种无描述，属既有状态，不是 bug） |
| 系列 | `series` 映射 **19** 个 key；`seriesKeys` 支持多系列（现有 3 个品种属多系列） |
| 套系 | `sets` **21** 个（同系列多枚的"套"，带 `size/kind=roll` 概念） |
| 图片 | `images.json`：`real` 135 个序号，`mock` = `[34, 56]`（这两个是占位图） |
| 导航 | 网站 7 个 tab：首页 / 发行计划 / 全套清单 / 全部系列 / 我的藏品 / 账号 / 管理。小程序页：index, list, series, plan, detail, holdings, mine… |
| 后端 | `server/index.js` 85KB / 1869 行手写 http 路由，40+ 接口（`/api/auth/*` `/api/holdings` `/api/state` `/api/series` `/api/prices` `/api/admin/*` `/api/visitors` …） |
| 已入库的部分 | `cl_meta` `cl_users` `cl_holdings` `cl_prices` `cl_visits`（用户/持仓/审计/访客/价格已在 MySQL） |
| 仍是静态文件 | `public/data/*.json`：coins 92KB / descriptions 261KB / gallery 15KB / plan 8KB / series 3.4KB / images 1KB |
| 小程序数据 | `tools/build_mp_data.js` 把上述 JSON 打包成 `miniprogram/data/catalog.js`（286KB 离线包） |
| 管理端 | 已有 品种参数(Params) / 图片(Images) / 系列(Series) / 发行管理(Plan) / 用户 / 反馈 / 访客 / 审计 / 封禁；**没有独立的贵金属录入页** |

**最关键的一条约束**：`i` 同时是「数组下标 / 图片文件名 / 路由 / 描述 key / sitemap 链接」五重身份。所以入库后 `no` 必须是**显式的一等列且 UNIQUE**，**新品种只能追加（no ≥ 138），任何情况下不允许插入或重排已有 no**——否则 `/coin/N` 全体错位、137 张图片全错、已收录的 SEO 页面集体失真。这是 P0 红线。

## 1. 产品目标

**一句话**：在不掉一个 SEO 页面、不破一个老接口、不让网站与小程序分叉的前提下，把品种目录从静态 JSON 迁成 MySQL 单一事实源，后端从手写路由升级为 Fastify 分层架构，并新增一个"可查可管、但不抢普通纪念币主角"的贵金属板块。

**3 条可衡量结果**

| # | 结果 | 衡量口径（可验收） |
|---|---|---|
| G1 | 数据零丢失、零漂移 | 迁移后行数对齐 137/128/19/21；137 条品种逐字段 diff **0 差异**；`no` 唯一且 1..137 连续；迁移脚本可重复执行（幂等，跑两次结果一致） |
| G2 | 对外契约零破坏 | ①`/coin/1`…`/coin/137`、`/`、`/all`、`/series`、`/plan` 共 141 个 URL 的 title / description / canonical / og / JSON-LD 与迁移前**逐字 diff 为空**；②40+ 接口路径/方法/状态码/响应结构不变，老前端**不改一行**跑通；③三端核心流程回归通过 |
| G3 | 贵金属上线且不喧宾夺主 | 首批 2–3 套真实数据三端可见；贵金属占目录 **≤10%**、首页与清单首屏曝光 **0 条**、默认排序不前置；管理端可完成"录入→编辑→上下架"全流程无需改代码 |

> 反向目标（明确不做）：不做前端重写、不改 UI 视觉、不做用户体系改造、不引入 ORM 之外的重量级框架、**不编造任何价格/发行量数据**。

## 2. 用户故事

**收藏者（已登录，有持仓与成本记录）**

1. 作为收藏者，我想在「全套清单」里按"普通纪念币 / 纪念钞 / 贵金属"筛选，这样我不用在 137 条里逐条辨认哪些是金银币。
2. 作为收藏者，我想在贵金属品种页看到克重、成色、材质、发行方式（预约/抽签/直销），这样我能判断这套值不值得参与。
3. 作为收藏者，我希望改版后我的持仓、套数、成本统计数字一分不差，这样我不会怀疑数据被动过。

**访客（未登录，多来自搜索引擎）**

4. 作为从百度点进 `/coin/N` 的访客，我看到的标题、摘要、面包屑与以前一致，能立刻确认这是我要找的那枚币。
5. 作为访客，我希望打开首页一眼看出"这是个普通纪念币站，另外还有一块贵金属"，而不是被金银币内容打断。
6. 作为访客，我不登录也要能看完全部品种和详情——这个现有能力不能因为重构而消失。

**管理员（运营）**

7. 作为管理员，我想在管理端新增/编辑贵金属品种（含克重、成色、发行方式），不用改 JSON、不用改代码、不用发版。
8. 作为管理员，我想改一条品种参数后网站和小程序同时生效，不用记得手动跑两次打包。
9. 作为管理员，我想在出问题时一键切回 JSON 只读模式，站点不至于挂掉，且能随时导出当前库的 JSON 快照留底。

## 4. 信息架构：贵金属怎么融进去而不喧宾夺主

### 4.1 板块定位
贵金属是**二级板块**，不是第 8 个顶级 Tab。逻辑位置：它属于"品种目录"这个容器下的一个类别，和"普通纪念币 / 纪念钞"平级，而不是和"首页 / 发行计划"平级。

### 4.2 五个入口的具体做法（"不喧宾夺主"落到可执行）

| 位置 | 做法 | 量化红线 |
|---|---|---|
| 首页 | 不新增 hero/推荐位。贵金属只以一个**系列卡**形式出现在现有系列区内（与"一轮生肖""国家公园"同规格同尺寸），卡片标题带"贵金属"字样 | 首页首屏贵金属条目 **0 条**；首页推荐/默认列表**不含**贵金属 |
| 全套清单 `/all` | 顶部加**类别分段控件**：`普通纪念币（默认）｜ 纪念钞 ｜ 贵金属`。默认落在"普通纪念币"，用户必须主动点一次才看到贵金属 | 贵金属占目录 **≤10%**；清单首屏可见贵金属 **0 条** |
| 全部系列 `/series` | 贵金属套系用独立 `seriesKey`（建议前缀 `PM`），`sort ≥ 200`，天然排在普通币系列（10/11/15/20…）之后 | 系列页首屏贵金属 **0 个** |
| 发行计划 `/plan` | **不进入**央行年度普通纪念币/钞计划清单（这是事实口径问题，不是偏好）。贵金属单独一个折叠区，默认收起 | 默认视图贵金属 **0 条** |
| 我的藏品 / 成本统计 | 数据层加 `category` 维度；**默认视图与默认统计口径完全不变**，另给一个"包含贵金属"开关 | 老用户成本总额改版前后 **数值不变** |
| 小程序 | 不加 tabbar 项（成本高、易挤版），入口在小程序 `list` 页顶部同样的分段控件，与网站同交互同排序 | 与网站一致 |

### 4.3 默认排序规则（三端统一，写进服务端一处）
```
ORDER BY category_rank ASC,   -- 普通纪念币=0, 纪念钞=1, 贵金属=2
         year DESC,
         no ASC
```
这条排序必须在**服务端统一出参**，网站与小程序都消费同一份，禁止各自排序（否则铁律必然破）。

### 4.4 URL 契约
贵金属详情**复用** `/coin/N`（`N ≥ 138`），不新开 `/pm/N`。理由：一套路由/一套 SEO 注入/一套 sitemap，维护成本最低，且 `no` 本来就是全局唯一序列。代价是 URL 上看不出品类——由面包屑和 JSON-LD `category` 补足。

### 5.2 贵金属必填 / 可空结论

- **必填**：`no`、`category`、`year`、`name`、`face`、`mintage`、`metal`、`purity`、`weight_g`、`is_set`、`source_url`、`source_date`、`verified`
- **条件必填**：`set_pieces`（当 `is_set=1`）
- **建议必填**：`issue_method`（用户最关心的信息之一，但历史数据可能查不到，允许 `unknown`）
- **可空**：`series/seriesKeys`、`spec`、`quality`、`sales_channel`、`dealer`、`certificate`、`packaging`、`set_weight_g`、`set_face_total`、`dia/size/thickness`、`caster`、`edge`、`obverse`、`reverse`、`est`
- **不复用 `sets` 表**：现有 `sets` 是"同系列多枚的套"（配 `size`/`kind=roll`，服务收藏者按卷统计）；贵金属套装是"一盒多枚"的售卖单元，语义不同，用 `is_set + set_pieces` 表达，避免一个字段两种含义。

### 5.3 数据录入要求（交给运营/主理人执行）
1. 每条贵金属品种**必须**贴 `source_url`（央行公告 / 中国金币网 / 中国金币总公司），`source_date` 取公告日期。
2. 克重、成色、面额、最大发行量四项以公告原文为准，**公告没有就不填，不允许估算或引用二手博客数字**。
3. `est`（估值）贵金属默认留空；如填必须带免责说明，且不得作为"行情"呈现。
4. 图片命名与普通品种同一规则，`no` 连续不跳号。

## 附：给架构师的三条硬提示

1. **`no` 是主键语义，不是自增 id 的副产品**。建议 `id` 自增主键 + `no` UNIQUE 双列，业务与路由一律用 `no`，永远不用 `id` 拼 URL。迁移时 `no = i + 1` 原样写入。
2. **排序必须服务端唯一出参**（`category_rank, year DESC, no`），网站和小程序都消费，这是"三端同步"铁律唯一可靠的落地方式。
3. **JSON 导出是回滚资产，不是遗留垃圾**。`export:json` 的产物结构应与现有 `public/data/*.json` **完全同构**，这样回滚开关才能真正一把切回、且前端零改动。
